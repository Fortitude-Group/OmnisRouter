# OmnisRouter tray-managed local proxy — design

**Created**: 2026-09-09
**Status**: Approved (brainstorm), feeds `/speckit-specify`
**Repo**: OmnisRouter

## Goal

Let a Windows user run the OmnisRouter routing proxy as a first-class tray app: installed
like any other app, running quietly from login, with a settings window for BYOK provider
keys and a one-click way to point their coding tools at it. No docker container, no console
window, no command line. The tray app that ships today does flat-rate usage collection only.
This adds the proxy alongside it in the same app, same tray icon.

## What exists today (grounding)

- `omnisrouter.exe` (built from `OmnisRouter.Api`, an ASP.NET Core app) is one self-contained
  binary that already serves the full proxy and also carries the `omnisrouter collect` command.
  Bare invocation (no args, or anything other than `collect`) starts the web host.
- `OmnisRouter.Tray` (WinForms, `net10.0-windows`) supervises the collect watcher **in-process**
  via `CollectEngine` on a background task with a 15s restart loop, enforces single-instance with
  a named mutex, auto-starts through a per-user Scheduled Task (`LoginTask.cs`), and stores config
  (Dashboard URL + DPAPI-protected project key) in `%APPDATA%\OmnisRouter\collect.json`.
- The router's BYOK keys are held in an AES-256-GCM encrypted EF column, master key in a local
  file (`%APPDATA%\OmnisRouter\master.key`), added via `POST /v1/keys` `{provider, label, api_key}`
  and never echoed back. Providers: Anthropic, OpenAI, Gemini, OpenRouter.
- Management endpoints (`/v1/keys`, `/v1/route`, routed traffic) require
  `Authorization: Bearer <router-token>`. `Omnis:BootstrapToken` seeds the first token when the
  token table is empty. The server has no hardcoded port and defaults its SQLite DB to the working
  directory, so both must be set on launch.
- The client rewrite (`--write`) lives in the npm helper (`installer/index.js`, Node), not .NET,
  and has no revert, only `.bak` backups.
- The per-user MSI (WiX, `Scope="perUser"`, installs to `%LOCALAPPDATA%\Programs\OmnisRouter`)
  harvests the whole tray publish folder, so bundling the server binary needs no `.wxs` change,
  only a staging step in the `windows` release job.

## Architecture

### Process model: supervise the server as a hidden child process

The tray does not host Kestrel in its own WinForms process. When the proxy toggle is on it
launches `omnisrouter.exe` as a hidden child `Process` (no window), supervises it with a restart
loop modelled on the existing `SuperviseAsync`, and stops it on quit. This reuses the entire
shipped router (routing model, ONNX embedder, upstream adapters, encrypted key store) untouched,
keeps the heavy ML runtime out of the UI process, and gives clean process isolation. Collect stays
in-process as it is today; only the proxy is a child process.

The server is launched with explicit settings the tray controls:

- `--urls http://127.0.0.1:<port>` (loopback only, default port `8787`).
- Working directory `%APPDATA%\OmnisRouter\router\` so `omnisrouter.db` lands there.
- `Omnis__BootstrapToken=<generated router token>` on first run to seed the management token.
- Master key path left at its default (`%APPDATA%\OmnisRouter\master.key`).

Loopback-only bind is a hard requirement: the local proxy must never be reachable off the machine.

### Ports and config

A validated port field in tray settings, default `127.0.0.1:8787` (deliberately not 8080, to
avoid clashing with a self-hosted docker router). Changing the port restarts the server and
re-points every currently connected client to the new URL. Port already in use at start is a
surfaced error state, not a silent failure.

New tray config in a sibling file `%APPDATA%\OmnisRouter\router.json` (kept separate from
`collect.json` so the two features' state never entangle):

- `RouterEnabled` (bool), `RouterPort` (int), `RouterToken` (DPAPI-protected, generated once),
  `ConnectedClients` (the set the tray has wired, for revert and for collector dedupe).

The router token is generated by the tray, DPAPI-protected at rest, seeded into the server as the
bootstrap token, and reused as the bearer for `/v1/keys` calls and as the auth token written into
connected clients.

### First-run ordering and readiness

Enabling the proxy must not let the keys window or a client-connect call race an unready server.
Sequence:

1. Ensure `%APPDATA%\OmnisRouter\router\` exists, generate the router token if absent.
2. Start `omnisrouter.exe`. The server runs its EF migration on startup.
3. Poll `GET /readyz` (and `/health`) on the loopback port until ready or a timeout.
4. Only then mark the proxy "Running", enable the keys window and Connect actions, and (if this is
   the first enable and no provider keys exist) open the keys window prompting for at least one key.

Any step failing lands the tray in a clear error state (amber icon, popup explains what failed)
rather than a half-up proxy.

## Tray UX

### Menu and two toggles

One tray icon, one context menu. Two independent switches:

- **Report usage to OmnisVigil** (today's collector).
- **Local router proxy** (new).

Either, both, or neither can be on, and each is remembered across restarts. Under the proxy toggle:
**Provider keys…**, **Connect an app…**, and the port field live in **Settings…**.

### Mode legibility (explicit requirement)

The user must never be unsure which mode they are in:

- The tray icon gets a distinct treatment when routing is live (a badge or accent on the lion),
  separate from the collector's green/amber/grey states.
- The status popup names the active mode in plain words: "Routing your traffic through your own
  provider keys (per-token billing)" versus "Reporting your flat-rate usage to OmnisVigil". When
  both are on it shows both lines and which clients are on which path.
- The first time routing is enabled, a confirmation explains that routed traffic uses BYOK keys and
  is billed per token by the provider, distinct from a flat-rate subscription, and requires a yes.

### Provider keys window

A small WinForms dialog listing the four supported providers (Anthropic, OpenAI, Gemini,
OpenRouter). Per provider: paste a key, save, see whether a key is set (never the value), and
remove. Save calls `POST /v1/keys` on the loopback port with the router token; remove calls
`DELETE /v1/keys/{id}`; the list reads `GET /v1/keys`. Keys are only ever held in the router's
AES-GCM store. The dialog shows the key value only in the input while typing and never reads it
back.

### Connect an app (C# rewrite + revert)

A submenu detecting installed clients and wiring each with one click, reusing the semantics of the
npm `--write` but reimplemented in C# so the tray needs no Node, and adding the revert the CLI
lacks. Each connected client is tracked in `ConnectedClients` for revert and dedupe.

- **Claude Code** → merge `ANTHROPIC_BASE_URL` (router root) and `ANTHROPIC_AUTH_TOKEN` (router
  token) into the `env` object of `~/.claude/settings.json`. Back up first, refuse on invalid JSON.
  Revert removes exactly those two keys (restoring any prior value captured at connect time).
- **Codex** → write a delimited managed block into `~/.codex/config.toml` defining
  `[model_providers.omnisrouter]` with `base_url = <url>/v1`, `env_key`, `wire_api = "chat"`.
  Idempotent. Revert deletes the managed block.
- **Cursor** → show-only. Cursor has no safe scriptable config, so the tray displays the base URL
  and token to paste into Cursor settings, with a copy button. "Connected" for Cursor means the
  user confirmed they pasted it (best-effort tracking), and revert just reminds them to clear it.

Revert is genuinely reversible for Claude Code and Codex because the tray captures the pre-connect
state at connect time.

## OmnisVigil integration and dedupe

When the proxy is on, the router reports its own content-free receipts (which carry the
savings-versus-frontier delta) to OmnisVigil using the existing project key, so routed spend and
savings appear on the dashboard. Configuration reuses the collector's project key from
`collect.json`; if the user has never set one up (proxy-only user), the tray prompts for it with
the same capture flow the collector uses.

Dedupe so nothing is counted twice:

- The collector tails Claude Code transcripts (its only source today). When a client is connected
  to the proxy, the tray excludes that client from the collector's scope, so routed traffic is
  reported once, by the router's accurate receipts, and un-routed clients stay with the collector.
- In practice, connecting Claude Code to the proxy removes Claude Code from the collector; the
  collector continues to cover anything else it can see. The set of excluded clients is the
  `ConnectedClients` set the tray already maintains for revert.
- Disconnecting a client returns it to the collector's scope.

## Packaging, release, install

- The `windows` release job additionally publishes `OmnisRouter.Api` self-contained for `win-x64`
  and stages `omnisrouter.exe` plus its `config/`, `routing/`, and `models/` (ONNX) sidecars into
  the tray publish folder before `wix build`. The MSI's existing `**` harvest packages them with no
  `.wxs` change.
- Accepted trade: the installer grows substantially (self-contained server plus the ONNX embedder).
  Still a per-user, no-elevation MSI. This is the deliberate cost of "no docker, works offline".
- Uninstall removes program files and the scheduled task as today, and leaves user data
  (`%APPDATA%\OmnisRouter\`, including the encrypted keys and DB) in place by default.
- Code-signing the bundled server and tray is desirable so SmartScreen and the child-process launch
  stay quiet, noted as a release concern.

## Error handling and edge cases

- Port already in use → error state, popup names the conflict, proxy stays off.
- Server crash → restart loop with backoff, matching the collector's supervision; repeated failure
  surfaces amber with the last error.
- Enabling routing with no provider keys → server runs but every route fails; the tray opens the
  keys window on first enable and warns while no key is set.
- Disabling the proxy while clients are still connected → warn and offer to revert those clients,
  so a client is not left pointing at a dead loopback port.
- Changing the port with clients connected → re-point all connected clients to the new URL.
- Uninstall while running → MSI closes the tray (as today), which stops the child server.

## Testing

- Client rewrite/revert: golden-file tests for Claude Code `settings.json` merge and Codex TOML
  managed block, including revert restoring the captured prior state, and the invalid-JSON refusal.
- Supervision: the child-process lifecycle (start, readiness poll, crash-restart, clean stop) with
  a stub server, no real ONNX load in the unit path.
- Keys window: talks to a stub `/v1/keys` and asserts request shapes and that the key value is
  never rendered back.
- Dedupe: connecting a client removes it from the collector scope and disconnecting restores it.
- Manual, not CI: a real end-to-end on Windows (install the MSI, enable proxy, add a real key,
  connect Claude Code, make a request, see the receipt on OmnisVigil), consistent with how the
  existing tray and live sign-in are verified by hand.

## Out of scope (this version)

- macOS and Linux desktop apps. Those platforms keep the `omnisrouter serve` CLI, and a menu-bar or
  indicator app is a later feature.
- A revert command in the npm CLI (the tray gets revert; the CLI is unchanged here).
- Multi-tenant or shared-network proxy use. This is a single-user loopback proxy.

## Open risks

- Installer size growth from bundling the server and embedder (accepted).
- Two secret stores under `%APPDATA%\OmnisRouter\` (DPAPI collector key, AES-GCM router master key)
  stay deliberately distinct; the design does not merge them.
- SmartScreen or AV friction on first launch of the bundled server without code-signing.
